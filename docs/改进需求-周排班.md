## 二、老师确认的四个细节

### 1. 班次时间（已确定，替换代码里的暂定值）

| 班次 | 时间 |
|---|---|
| Morning 早班 | **08:00 – 12:00** |
| Afternoon 中班 | **14:00 – 18:00** |
| Evening 晚班 | **20:00 – 22:00** |

> 注意：**都不跨天**，比原暂定值（晚班 20:00-02:00）简单，不需要跨天处理。

### 2. 一个员工一天可以排多个班

老师原话："一个员工一天可以多次排班"

**这直接改变数据模型**：

```sql
-- 错：一人一天一条
UNIQUE(employee_id, work_date)

-- 对：一人一天每个班次一条（可同时排早班和晚班）
UNIQUE(employee_id, work_date, shift_name)
```

### 3. 按周显示，带日期，可翻上下周

URL 用 `?week=2026-10-13` 这种形式（传该周任意一天即可，内部换算成周一）。

### 4. 三个角色的视图（最终确认版）

| 角色 | 视图 | 说明 |
|---|---|---|
| **普通员工** | 个人周课表：**行=三个班次，列=周一到周日** | 只读。格子里打勾表示这天这个班要上班 |
| **Supervisor** | 全店视图：**按天分组，每天列出三个班次分别有哪些员工**，并显示员工基本信息 | 只读总览。**要修改排班就点进员工详情页编辑** |
| **HR** | 全店视图：按员工分组，看每个人一周的班次 | 只读，可筛选（按班次、按员工名）|

> 关键差异：主管是"**按天看谁在上班**"（排班视角），HR 是"**按人看他这周上什么班**"（人事视角），员工是"**我自己的课表**"。

## 三、数据模型改动

### 表结构

```sql
CREATE TABLE shifts (
    id          INTEGER PRIMARY KEY AUTOINCREMENT,
    employee_id INTEGER NOT NULL REFERENCES employees(id) ON DELETE CASCADE,
    work_date   TEXT    NOT NULL,          -- 'YYYY-MM-DD'
    shift_name  TEXT    NOT NULL CHECK (shift_name IN ('Morning','Afternoon','Evening')),
    assigned_at TEXT    NOT NULL,
    assigned_by TEXT    NOT NULL DEFAULT ''
);

-- 一人一天一个班次一条；同一人同一天可有多条（不同班次）
CREATE UNIQUE INDEX idx_shifts_employee_date_shift
    ON shifts(employee_id, work_date, shift_name);
CREATE INDEX idx_shifts_work_date ON shifts(work_date);
```

### 迁移

`initialize()` 里检测旧表结构（无 `work_date` 列），若为旧结构则 `DROP TABLE shifts` 重建。
员工与账号数据不受影响；排班数据因无日期无法迁移，用种子数据重建。

### 种子数据

为演示员工生成**当前周**的排班：
- 每个员工按原 `shift` 值，周一至周五各一天
- 另外给 1–2 个员工在**同一天排两个班**（早班+晚班），用来演示"一天多班"
- 保留 1 个员工整周为空，用来演示空格子

## 七、验收时的说法

> "老师建议后，我们把排班从『每个员工一个当前班次』升级成了**按日期的周排班**，
> 并针对三个角色做了三种不同的视图：员工看自己的周课表，主管按天看全店谁在上班，
> 人事按人看每个人这周的班次。修改排班在员工详情页进行，避免在全店视图里误改。"
