## 2.1 Dylan（金俊臣）— 员工信息模块 + 系统骨架

### 负责什么
员工档案的增删改查、数据校验、首页与统计，以及整个应用的请求处理骨架（路由、权限、会话）。

### 关键文件

| 文件 | 行数 | 内容 |
|---|---|---|
| `app/views.py` | 543 | `employee_create` / `employee_edit` / `employee_delete` / `employee_overview` / `employee_detail` / `home` / `statistics` |
| `app/htmlpages.py` | 171 | `validate_employee()` 校验规则、`format_currency()` 显示格式 |
| `app/app.py` | 441 | 路由表、`_authorize()` 角色校验、`_check_csrf()` 防伪造 |
| `app/security.py` | 191 | `hash_password()` PBKDF2 加盐、`SessionStore` 会话管理 |

### 核心逻辑（一句话）
**请求进来 → 路由匹配 → 查角色是否允许 → 校验 CSRF → 调视图函数 → 视图用仓储读写数据库 → 渲染模板返回。**

### 20 秒自述稿
> "我负责员工信息模块和系统骨架。员工模块的核心是增删改查四个操作，全部由 HR 角色独占。数据校验我做在服务端：姓名、地址、时薪都有具体的长度和范围规则，校验失败时逐字段返回可读的提示，并且保留用户已经填好的内容——这是 URS 用例 1A 的要求。系统骨架方面，每条路由都声明了允许的角色，权限在服务端统一拦截。"

### 2 分钟版补充要点
- **校验规则为什么这么定**：姓名 2–60 字符、地址 5–120、时薪 1–1000。不是拍脑袋，是为了挡住明显错误（空值、负工资、误按小数点），同时不卡住正常输入。
- **为什么要保留用户输入**：URS 用例 1A 明确要求"系统停留在输入表单并保留已输入数据"。实现方式是校验失败时重新渲染表单，把提交的值回填。
- **权限为什么在服务端**：前端隐藏按钮只是体验，真正的拦截在 `_authorize()`。手动敲 URL 也会被 403。

### 可能被问
**Q: 校验为什么不用前端的 required？**
> A: 前端校验我们也用了（HTML 的 required、type=number），但它可以被绕过（改 HTML 或直接发请求）。所以真正的校验必须在服务端做，前端只是提前反馈。NFR04 也要求错误提示友好，服务端能给出具体文案。

**Q: 为什么时薪上限设 1000？**
> A: 这是业务假设：这是五金店员工的小时工资，1000 元/小时明显是输入错误。设上限是为了挡住误输入（比如多打了几个零）。这个值写在 `htmlpages.py` 里，是常量，改起来很容易。

## 2.2 Morty（王志远）— 数据库后端

### 负责什么
数据库结构设计、所有 SQL 语句、连接管理、演示数据初始化。

### 关键文件

| 文件 | 行数 | 内容 |
|---|---|---|
| `app/database.py` | 约 460 | 三张表的 `SCHEMA`、`connect()`、`initialize()`（含旧表迁移）、`seed()`、班次时间 `SHIFT_TIMES` |
| `app/repositories.py` | 约 500 | 全部 SQL：`create_employee` / `search_employees` / `assign_shift` / `week_dates` / `day_roster` / `employee_roster` / `week_summary_counts` 等 |

### 表结构（能背下来最好）

```
users      账号：id, username, password_hash, display_name, role, employee_id
employees  员工：id, name, address, hourly_wage, phone, email, hired_on, created_at, updated_at
shifts     排班：id, employee_id → employees(id) ON DELETE CASCADE,
                  work_date 'YYYY-MM-DD',
                  shift_name CHECK IN (Morning/Afternoon/Evening),
                  assigned_at, assigned_by
           唯一索引 (employee_id, work_date, shift_name)
```

三个关键设计：
1. **`role` 有 CHECK 约束**：数据库层面只允许三个角色值，程序写错也存不进去。
2. **`employee_id` 外键 ON DELETE CASCADE**：删员工时该员工的所有排班自动删除，不会留下孤立数据。
3. **三列唯一索引 `(employee_id, work_date, shift_name)`**：一人一天一个班次只能有一条记录，但同一天可以同时排早班和晚班（老师演示后确认的要求）。

### 20 秒自述稿
> "我负责数据库设计和所有 SQL。系统用 SQLite，三张表：账号、员工、排班。两个我认为关键的约束：一是角色的 CHECK 约束，数据库层面只接受三个合法角色；二是排班表对员工的**外键级联删除**，删员工时关联排班自动清理，这直接对应 URS 用例 5 第三步的要求。老师演示后我们把排班从"一个当前班次"改成**按日期的周排班**，唯一索引是员工 + 日期 + 班次三列，所以一个人一天可以排多个班。所有查询都用参数化写法，防 SQL 注入。"

### 2 分钟版补充要点
- **为什么 SQLite 而不是 MySQL**：这是单店内部工具，最多 10 个并发用户，SQLite 完全够用，而且**零配置、单文件**——客户拿到就能用，不需要装数据库服务。备份就是把一个文件复制走。
- **为什么按日期存**：老师要求"员工像课表一样看到自己哪天什么时间段工作"，所以每条记录带 `work_date`；查询用 `BETWEEN 周一 AND 周日` 取一周，日期索引 `idx_shifts_work_date`。
- **旧数据库怎么升级**：启动时 `initialize()` 检测旧的 `shifts` 表（没有 `work_date` 列）就重建表，并按当前周重排演示数据；员工和账号数据完全不动。旧排班没有日期，无法迁移。
- **搜索怎么做的**：`LIKE '%关键词%'` 匹配姓名、地址、电话、邮箱，配合索引。实测 400+ 条记录下响应远低于 2 秒。

### 可能被问
**Q: 怎么防 SQL 注入？**
> A: 全部用参数化查询（`?` 或命名占位符），从不拼接用户输入到 SQL 字符串。比如 `WHERE name LIKE :pattern`，参数单独传进去，数据库驱动负责转义。

**Q: 一个员工能有多个班次吗？**
> A: 能，而且是老师确认的重点需求。一条排班记录 = 员工 + 日期 + 班次，唯一索引是这三列；同一天排早班和晚班是两条独立记录，可以分别删除。演示数据里 Li Wei 周三就是早班 + 晚班。

**Q: 删除员工排班怎么办？**
> A: 外键 `ON DELETE CASCADE`，数据库自动删掉该员工的所有排班记录。这是 URS 用例 5 明确要求的。

**Q: 数据存在哪，能备份吗？**
> A: 单个文件 `data/employee_management.db`。备份就是复制这个文件，恢复就是放回去。

## 2.3 Spring（王春希）— 周排班模块

### 负责什么
主管周排班（按日期加/删班次）、单人整周排班查看、全店周排班三种角色视图、普通员工的个人周课表。

### 关键文件

| 文件 | 内容 |
|---|---|
| `app/views.py` | `employee_assign_shift()`、`employee_clear_shift()`、`store_shifts()`、`my_shifts()`、`_week_context()`、`_own_week_context()` |
| `app/repositories.py` | `assign_shift()`、`clear_shift()`、`employee_week_shifts()`、`week_dates()`、`day_roster()`、`employee_roster()`、`week_summary_counts()` |
| `templates/employee_detail.html` | 排班面板（日期 + 班次下拉框 + 确认按钮），下方整周列表每行可删除 |
| `templates/store_shifts.html` | 全店周排班：主管按天分组 / HR 按员工分组 + 筛选 |
| `templates/my_shifts.html` | 个人周课表（行=班次，列=周一到周日）|

### 核心逻辑
排班只有 **Supervisor** 能做。面板在员工详情页：选**日期** + 选三个固定班次之一 → 提交写入 `shifts`（员工 + 日期 + 班次），记录**谁在什么时候**确认；下方列出该员工**整周**排班，每行有自己的删除按钮，删一条不影响同一天的另一条。

**关键设计：** 全店排班总览页**故意不提供修改控件**——因为 URS 第 6 节明确要求"shift-modification controls are hidden"，排班只能从员工详情页进行，避免在总览页误改。

**三种视图（老师确认的最终版）**：
- 员工：个人周课表，行=三个班次，列=周一到周日，格子打勾；
- 主管：按天分组，每天列出三个班次分别有谁（排班视角）；
- HR：按员工分组，看每个人一周的班次，可按班次和姓名筛选（人事视角）。

### 20 秒自述稿
> "我负责周排班模块。核心是三点：第一，排班权限只给 Supervisor——HR 虽然能管员工档案，但 URS 明确规定日常排班是主管的事，两者职责分离。第二，老师演示后我们改成**按日期的周排班**：一条记录是员工 + 日期 + 班次，所以一个人一天可以排多个班，员工看到的是一张真正的周课表。第三，三个角色三种视图：员工看自己的课表，主管按天看全店，HR 按人看整周。每次排班都记录操作人和时间。全店视图故意不放修改控件，避免误改。"

### 2 分钟版补充要点
- **重复排班怎么处理**：`INSERT ... ON CONFLICT(employee_id, work_date, shift_name) DO UPDATE`，同样的员工+日期+班次再次提交只刷新确认人和时间，不会出现重复行。
- **删除怎么实现**：整周列表每行一个独立的删除表单（员工 + 日期 + 班次），只删那一行；同一天的其他班次保留。
- **怎么翻周**：所有周视图接受 `?week=YYYY-MM-DD`（该周任意一天即可，内部换算成周一），页面右上角有上一周 / 下一周 / 本周。
- **员工只能看自己的**：`my_shifts()` 用会话里的 `employee_id` 查，不接受 URL 参数，所以无法通过改地址看别人的。

### 可能被问
**Q: 为什么 HR 不能排班？**
> A: URS 第 3 节的权限表明确写了 HR "Cannot assign work shifts"，用例 2 的 Actor 也只有 Supervisor。我们按文档实现，并且在服务端强制——HR 直接发请求也会被 403。

**Q: 员工能不能看到别人的排班？**
> A: 不能。普通员工的"我的班次"只根据登录会话里的 employee_id 查询，页面上没有任何员工列表。手动访问 `/employees/1`（员工详情）会被 403。

**Q: 如果排班排错了怎么办？**
> A: 主管在员工详情页的整周列表里点那一行的 Remove 删掉，或者重新排一条。每次修改都会更新操作人和时间。

**Q: 班次时间是多少？**
> A: 老师演示后确认：早班 08:00–12:00、中班 14:00–18:00、晚班 20:00–22:00，都不跨天。

# 三、系统架构（任何人都可能被问到）

```
浏览器
  ↓ HTTP
app/server.py          线程化 WSGI 服务器
  ↓
app/app.py             路由匹配 → 角色校验 → CSRF 校验 → 错误处理
  ↓
app/views.py           每个页面的处理逻辑
  ↓
app/repositories.py    全部 SQL
  ↓
SQLite 文件 data/employee_management.db
```

**一句话版本**：分层架构，请求从服务器进来，经过统一的路由和权限层，再交给页面处理函数，页面函数通过仓储层读写数据库，最后渲染模板返回。

**为什么这么分层**：改页面逻辑只动 `views.py`，改 SQL 只动 `repositories.py`，职责清楚，也方便分别测试。

# 四、问答库

## 技术与选型

**Q1: 为什么不用 Flask / Django？**
> A: 项目要求"PyCharm 里直接运行、不需要装任何东西"。用标准库可以做到零依赖，队友和监督老师 clone 下来就能跑，不用配环境。代价是我们自己写了一个小型 WSGI 框架和模板引擎，但这也让我们完全掌握每一层在做什么。

**Q2: 自己写的模板引擎可靠吗？**
> A: 它有 10 个专门的单元测试（`tests/test_templateengine.py`），覆盖继承、块、循环、转义、错误处理。最重要的是**默认开启 HTML 转义**，防止 XSS。

**Q3: 密码怎么存的？**
> A: PBKDF2-HMAC-SHA256，每个密码独立的随机盐，20 万次迭代，存的是哈希不是明文。校验用常量时间比较，防止时序攻击。

**Q4: 会话怎么管？**
> A: 服务端存会话（内存字典），浏览器只拿一个随机令牌放在 HttpOnly Cookie 里。所以浏览器改不了自己的角色。

**Q5: CSRF 是什么，怎么防的？**
> A: 跨站请求伪造。我们每个表单都带一个随会话生成的令牌，提交时服务端校验，不匹配就拒绝（返回 400），数据不动。可以现场演示：伪造令牌提交会被拦。

## 需求与范围

**Q6: URS 写的是 desktop-only，为什么交网站？**
> A: URS 1.0/1.1 确实写的是桌面程序。开发中我们向老师确认，本地运行的网页应用同样满足验收标准——服务只在本机启动、不对外网暴露、数据存本地。确认后我们发布了 **URS 1.2**，在文档变更记录里写明了这次修订的原因。老师演示后的周排班建议又形成了 **URS 1.3**（班次时间、按日期的周排班、三种角色视图）。都是需求变更，有记录可查。

**Q7: URS 列了四个角色，为什么只有三个？**
> A: 第四个是 Depot worker（仓库工人），URS 表格里我们自己标注了 "Out-of-scope for current iteration"，预留给后续的库存管理迭代。本迭代实现的是 HR、Supervisor、Ordinary Employee 三个角色，对应 FR01–FR13。

**Q8: 为什么 HR 不能排班？**
> A: 这是 URS 第 3 节的权限定义：HR 负责人事档案的增删改，排班是主管的日常职责，两者分离。用例 2 的 Actor 只有 Supervisor。

**Q9: 哪些功能没做？**
> A: FR14–FR18，在 URS 里标注为 Won't-have：部门管理、店内考勤、自动排班、库存管理、员工自助网站。这些是**有意不做**，属于后续版本范围。

## 非功能需求

**Q10: 2 秒响应怎么保证的？**
> A: 我写了专门的测试（`test_nonfunctional.py`），插入 400+ 条员工数据后测量列表页和搜索页的响应时间，断言低于 2 秒。实际远低于这个阈值。数据库对姓名建了索引。

**Q11: 10 个并发用户怎么测的？**
> A: 开了 10 个线程同时登录并请求页面，全部返回 200，并且确认产生了 10 个独立会话。服务器是线程化的，每个请求一个线程。

**Q12: 数据会丢吗？**
> A: 不会。数据存 SQLite 文件，重启后还在——这个我们用一个脚本**真的停止服务器再启动**验证过。

**Q13: 测试做了多少？**
> A: 137 个自动化测试全部通过，另有 40 项端到端 HTTP 检查和 7 项持久化检查。测试计划文档里有 60 条测试用例和完整的需求追溯矩阵。

## 可能的追问

**Q14: 员工重名怎么办？**
> A: 每个员工有唯一的 id（员工编号），列表和详情页都显示编号，所以重名不影响识别和操作。测试里专门验证了这一点。

**Q15: 如果两个主管同时改同一个员工的班次？**
> A: 如果改的是同一条（员工 + 日期 + 班次），后提交的覆盖先提交的，最后一次生效；如果排的是同一天的不同班次，两条都会保留。这个场景在 10 用户并发范围内，SQLite 会串行化写入，不会写坏数据。

**Q16: 怎么部署到店里？**
> A: 店里的电脑装 Python，把项目文件夹拷过去，运行 `python app.py`。浏览器访问本机地址即可。不需要装数据库，不需要联网。
